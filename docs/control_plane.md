# V1 control plane

## 文档变更的影响范围与旧项目恢复

文档撰写方案只依赖明确指定的上游文档。已有验证资料可供查阅，但不能因为出现在资料清单中，
就把全部文档相互设为变更依据；正文也不能成为自身撰写方案的输入。正文变化仍使本次正文验收
以及真正依赖它的下游结果需要重新核验，RTL、规格和明确上游文档变化仍按实际关系传播。

旧项目出现一份正文修改导致所有工作流进度归零时，Agent 可先执行 `docs repair-dependencies`
预览修正，再使用 `--apply` 保存。操作保留方案、节点、版本、审批和历史正文，只纠正错误的
文档依赖，并处理可以证明由这些错误关系产生的变更通知。恢复完成状态前必须核对原已验收
版本、当前输入、正文、负责人批准及完整 Agent 检查；其他问题、审批意见和真实内容变化继续
阻止完成。修复过程记录原依赖、相关变更通知和沿用的审批，不生成新的负责人批准。

下游代码与证据仍由正常检查逻辑核验，因此修复依赖不保证所有工作流恢复为 100%。

## VENV、VSTIM、VCHK、VCASE、VCOV、VREG 方案与交付验收

六类验证工作流主页面参照 VDOC：当前项目状态、工作节点列表，以及添加节点、删除节点和
重新启动工作流。VENV、VSTIM、VCHK、VCASE 按 DUT 工作范围建立代码实现方案和
对应代码交付验收节点，VCOV 使用覆盖率实现方案、覆盖率实现交付、覆盖率收敛方案、
覆盖率收敛交付四种节点类型；VREG 使用回归基础设施方案、回归基础设施交付、回归结果方案、
回归结果交付四种节点类型。实际节点数量按 DUT 的验证范围决定。列表使用百分比圆环，负责人批准后只收起详情，
不会关闭浏览器标签页。产物和 CAP 不另计工作节点或进度。
所有公开方案与交付节点的列表行都提供“批准全部内容”，与详情共用审批条件和确认弹窗。
前置依赖、验证证据或审批意见尚未满足时，列表和详情均禁用按钮并说明原因。
打开审批节点时，Dashboard 按同一项目、当前节点和内容版本，与**最近一次负责人批准的内容**比较。
未批准的中间版本不作为基准；同一 revision 内的变化也会显示。方案、文档正文、交付代码、
原始证据、逐项检查结果、实际依赖版本和回归执行轮次均纳入各自节点的对照范围。
在节点抽屉、完整节点页面和批准确认弹窗中，先总结新增、删除、修改了什么，再提供完整差异对照。
只对新增或修改的文字片段加黄色下划线，删除的文字使用删除线；相同的文字、条目和栏目保持普通显示。
只调整列表顺序时单独说明，原有内容不高亮。文件变化列出受影响的路径，摘要变化可在完整差异中核对；
没有保存旧文件正文时，不声称提供代码行级差异。超长文本不能精确比较时显示完整前后内容，不猜测高亮。
负责人批准时，在同一事务中保存不可变的审批内容快照。旧审批仅从绑定该审批回执的历史产物恢复内容，
缺失的历史快照明确标为无法核实，不能拿当前文件冒充旧文件，也不能把“无法比较”显示成“没有变化”。
尚无批准记录时按首次审批处理。对照不授予批准；读取失败或当前版本已变化时，确认弹窗禁止提交。

VCASE 的 `HoleAnalysisReport/1` 是提出补洞工作范围的历史反馈：当前已批准方案使用批准时的报告版本，
后续报告生成时间、其他未覆盖项或覆盖进展变化不自动重写该用例方案。新未覆盖项通过 Main Agent 分析并显式调整
工作范围；真实范围、规格、代码、原始证据、检查结论或实际依赖版本变化仍重新核对和审批。
报告路径、批准时摘要和审批回执保存在 `code_feedback_inputs`，同一工作包的交付使用这一历史依据。
VCASE 保留这一专用反馈报告的默认识别。其他代码方案可以通过 `planning_feedback_files` 显式列出
仅用于提出工作范围的 `HoleAnalysisReport/1`，这些路径必须同时属于 `input_files`，并随方案由负责人批准。
不允许将 RTL、未知报告、本节点输出或实际验证证据标为规划反馈；未显式声明的其他输入仍逐字节核对。
正文、代码、原始证据和专用检查报告不做通用“忽略时间戳”或文字相似度判断。
首次升级仅在现存报告字节与原批准产物一致时补建绑定，否则保持阻塞，不猜测旧报告的类型。
新节点和显式重启不继承旧绑定或旧批准。回执、登记时间和描述性报告更新仍保留审计记录，不单独触发重复验收。

所有公开节点通过同一 `validity` 投影区分原批准是否有效、证据是否为当前版本、当前是否可用和是否需要重新审批。
批准有效不表示节点已完成：依赖暂时不可用、待处理意见、未完成的正文检查仍阻止推进。
文档与代码产物暂时撤销时保存最后一次有效版本 `last_current`，仅用于核对原批准的依赖身份；
`current` 仍为空，能力仍不可用，不允许用历史版本启动实施或通过验收。
恢复到相同有效版本时沿用原批准；恢复为不同版本、真实输入或范围变化时仍重新核对并要求相应审批。
历史版本缺失时不猜测，也不以最新文件替代已批准依据。

方案输入不得包含本节点交付输出（包括输出目录中的文件），避免生成报告后反过来使方案审批失效。
登记时拒绝这类方案；已有冲突节点阻止批准并要求修订输入与输出范围，不自动删除登记或继承批准。
未覆盖项分析报告作为覆盖率收敛交付证据时应登记在输出和验证证据中，而不是该节点的方案输入。

方案正文固定为目标、工作范围、具体工作、实现方式、如何验证、输出、交付条件。
输入依据默认折叠，代码只列目录，文档逐一列出。待确认事项由 Agent 关联节点
单独提问，不作为方案正文栏目。方案批准后才能在对应交付节点实现和验证。

交付节点以验证报告和证据替换文档正文，展示检查方法、预期、实际结果和结论，
并提供当前交付文件和证据的受控查看入口；覆盖率收敛交付展示数据库、采集报告和未覆盖项处理结论，
回归结果交付展示测试清单、执行报告和失败处理记录。
Agent 完成验证后才允许负责人批准；验证
失败、证据缺失或内容变化时不能批准。批准说明选填，审批意见按批提交给 Agent，
全部处理完成后才能重新批准。负责人批准后不再要求常规 Agent 验收后检查。

依赖统一为 `上游 cap → 方案节点 → art.code_plan → 交付节点 → art.code → cap.<workstream>`。
VSTIM 依赖 VENV，VCHK 依赖 VENV 和 VSTIM，VCASE 依赖 VENV、VSTIM 和 VCHK；
VCASE 自身验收不等待 VCOV，VCOV 在后续消费已验收的用例和运行证据。代码或证据变化只撤销受影响交付及 CAP，上游文档、
输入或方案变化则同时撤销方案与交付。所有批准都绑定具体版本。

Agent 使用 `plan WORKSTREAM --desired-file proposal.json` 提交代码方案，使用
`code status NODE` 读取当前验证对象，使用 `code validate NODE report.json` 登记
实际验证报告，使用 `code artifacts` 查询历史与当前可用状态。该命令不会运行
仿真或自动批准。完整字段与证据要求见
[VENV](../skills/verif-harness/vplan/venv.md)、
[VSTIM](../skills/verif-harness/vplan/vstim.md)、
[VCHK](../skills/verif-harness/vplan/vchk.md)、
[VCASE](../skills/verif-harness/vplan/vcase.md)、
[VCOV](../skills/verif-harness/vplan/vcov.md) 和
[VREG](../skills/verif-harness/vplan/vreg.md) 使用说明。

同一节点在方案、上游输入、代码、证据和检查结论均未变化时，再次登记相同验证报告
只增加审计回执，不撤销负责人已完成的交付验收，也不生成新的交付能力版本或待办。
回执编号和登记时间不属于验收对象；证据内容或执行轮次变化后，仍需重新验证并由负责人
验收。已保存的旧回执编号绑定审批按原证据内容核对，不能借此沿用其他版本的审批。

VCOV 按“覆盖率实现方案 → 实现交付 → 收敛方案 → 收敛交付”推进。实现交付验收后，Engine
派生有效的 `cap.vcov:coverage-model` 和 `cap.vcov:coverage-collection` 汇总能力；收敛方案
使用 `cap.vcov:<implementation_key>` 关联具体已验收实现范围，不能只依赖汇总状态；
这些能力是内部派生状态，不增加公开节点或审批入口。当前必需的实现和收敛两部分都完成验收后，
VCOV 才满足完成条件，只实现覆盖模型不能完成整条工作流。

负责人在实现方案中审批 `CoverageScope/1`，而不是逐条审批 simulator 的 line、toggle、
bin 和 cross。code coverage 范围由 metric、层次选择或 `cm.hier` 类文件及范围内排除配置
组成；functional coverage 范围由 covergroup 选择规则和必需对象类型组成。
`CoverageImplementationConfig/1` 固定覆盖率插桩、elaboration、采集、导出和分析配置、
工具版本以及兼容 submit profile 摘要；code coverage 的目标固定为 DUT，不统计 testbench
代码。xverif 使用当前计划、实现配置和模型展开
`CoverageObjectInventory/2`，模型、采集与未覆盖项分析证据通过
`coverage_inventory_digest` 绑定同一份受控对象全集。收敛报告保存完整计数，只逐项列出
excluded/uncovered 未覆盖项；计数、清单、计划、模型或数据库不一致都会阻止收敛。
收敛方案继承明确关联的已验收实现范围，不能自行缩小批准范围。
`CoverageCollectionConfig/1` 只读引用一条或多条 VREG `regression_config` 和 merge profile；
case、submit profile、seed 与 repeat 只在 VREG 审批。VREG 轮次产生的 VDB 由
`CoverageDatabaseShardManifest/1` 绑定 batch/case/seed/iteration，随后由
`CoverageMergeManifest/1` 证明全部分片进入同一个合并数据库。
是否允许 merge 只看 DUT 构建指纹：DUT RTL、parameter、宏和 DUT 级 elaboration 必须一致；
其中任何一项不同都禁止 merge。testbench、submit profile 和 DUT 实例路径不进入该指纹，
所以相同 DUT 可以由不同 testbench/profile 采集后合并；各来源仍须分别绑定 VREG 方案、执行轮次
和 batch，merge 工具错误仍会阻止交付验收。
一个覆盖率收敛方案及其对应交付只管理一个批准的 DUT 指纹分区。预期存在多个指纹时，Agent
在 proposal 中分别建立多个覆盖率收敛方案，批准后各自产生一个收敛交付；VDB、batch、case、
seed 和 iteration 仍保留在节点内部清单，不转换成公开节点或额外审批。
如果未覆盖项处理结论包含 excluded 项，负责人先在收敛交付节点提供 exclude 文件；提供即表示
文件中的排除范围已经人工审批，不再为每个排除项重复建立 WAIVE。CLI 对应命令为
`code provide-exclusions NODE FILE --reviewer NAME --confirm`，Dashboard 提供同一受控入口。
Agent 随后用 `code validate` 检查文件合法性、当前 revision/节点绑定，以及未覆盖项分析报告是否引用
相同路径、SHA-256 和同一个文件级审批记录。替换或修改文件会使旧 validation 和交付验收失效。
最终覆盖率收敛结果仍由负责人单独验收。
Dashboard 的覆盖率收敛交付节点依次展示检查范围、结果报告、未覆盖项说明、
排除项说明、检查与验收，五部分均默认折叠，点击标题展开。数量和逐项说明取自 Agent 已检查的报告；过期报告会
标明不能据此验收，缺失的原因不由页面猜测。长摘要按分号和句号分条展示，
并默认收起；负责人可展开查看报告原文和逐项检查依据。主要页面使用易懂的
说明；Agent 的长段问题说明也按句分段。原始报告和审计记录仍保持原样。
排版不改变检查结论或验收条件。
其他工作节点采用相同的阅读方式：文档撰写内容、文档正文、代码方案各部分、
覆盖率和回归配置、交付文件、报告摘要、逐项检查、完成条件及变化明细默认折叠。
当前状态、检查结论、待处理问题、审批按钮和回归操作保持可见；抽屉和完整节点页
共用同一展示。正文仍在打开节点时通过受控接口读取并核对版本，折叠不会延迟或
绕过审批检查；读取失败及版本变化提示保持可见。
旧 `CoverageEvidence/1`、`CoverageEvidence/2`、`CoverageObjectInventory/1` 和
`CoverageItemManifest/1` 记录继续保留用于审计，但不能满足当前
交付；缺少当前合同信息时必须重新验证，过期未覆盖项分析报告不再触发反馈动作。
VCASE 中的完整 case 由 testcase 或可执行 virtual sequence 与一个 submit profile
共同确定。submit file 是 testbench 的配置事实源；verif-harness 只记录项目内路径、
profile ID、submit file 摘要和 profile 摘要，不复制、解析或执行 VCS、LSF、license
与站点 wrapper 配置。同一 testcase 可以用多个 `CaseManifest/2` 分别绑定不同
profile。testbench 的 submit 工具再生成 `RegressionBatchManifest/2` 和 caselist；每个
batch 只绑定一个 profile，因此同一组 case 使用不同 profile 时必须成为不同
batch/caselist。执行和分类记录以 batch、case、seed 和 iteration 联合标识。
每个 `CaseManifest/2` 还通过 `traceability` 关联已有用例清单、验证点以及规格、RTL、未覆盖项、
缺陷、参考模型或工程决定的文件、SHA-256、版本和位置，单独记录预期结果及检查依据。
仅由 RTL 推导的行为标记“RTL 推导，尚未确认”，确认前不得通过 VCASE 交付验证；需要确认时复用
本节点既有提问，回答必须匹配同一 case 的具体来源和预期版本。未覆盖项反馈使用受控历史快照。
来源、预期依据或确认记录变化会使相关证据需要重新核对。原 CaseManifest/1 仅保留历史，
升级后需补齐真实来源重新验证；不为每个 case 增加公开节点或审批入口。
VREG 按“回归基础设施方案 → 基础设施交付 → 结果方案 → 结果交付”推进。基础设施只依赖
已验收文档和环境；验收后派生有效的 `cap.vreg:executor-ready` 汇总能力。结果方案通过
`cap.vreg:<implementation_key>` 明确关联当前方案中的已验收基础设施范围，同时依赖当前
文档、环境、激励、检查、用例和 `cap.vcov:coverage-collection`，基础设施不反向等待最终结果。
VREG 当前轮次验证完成后即可向 VCOV 提供 VDB；VREG 结果交付的最终人工验收再等待当前
覆盖率采集与未覆盖项分析能力，避免执行和收敛形成依赖环。必需基础设施和结果
节点都完成验收后，VREG 才满足完成条件，执行器可用不等于整条 VREG 完成。
VSTIM、VCASE 和 VCOV 如需回归执行能力，只能依赖 `cap.vreg:executor-ready`，不能把
`fresh-evidence` 等最终回归结果反向作为上游。每次登记代码方案前，Engine 会把当前各工作流
的实现范围能力和汇总能力展开为一张项目级依赖图；发现跨工作流循环时整次登记失败，旧 revision
继续有效，不会保存一张可能互相等待的图。
结果验证必须核对执行失败与分类记录的 batch/case/seed/iteration 一致性，以及当前 VREG 版本的真实例外
批准。Engine 派生当前必需上游证据清单，并在读取和验收时重新核对；报告不得自行缩小范围。
结果交付不等待自身或其他结果交付先验收，所有结果的最终验收由整体完成条件检查。
旧结果验证记录保留，缺少 `RegressionResults/4` 合同时必须重新验证。
结果方案按 group（case 集合＋一个 submit profile）一一分解，基础设施可复用。
方案中的 `regression_config` 将 case/profile 版本和运行参数一起纳入批准：随机 seed
模式每次保存新实际 seed，指定模式每次使用同一个 seed；repeat 为每个 case 的计划
总次数，正整数，默认 1。保存、重跑和复现由已有回归脚本实现，控制面只核对合同和证据。
参数改变需重新审批，按批准随机策略生成 seed 不算修改方案。

“按已批准方案重新回归”只在结果交付节点提供，与验收结果分开。负责人再次确认后
通过 `/api/code/regression-rerun` 或 `code rerun` 登记同一 ProjectStore 执行请求；
请求绑定当前节点、批准版本、内容摘要和幂等标识。失效依赖、有阻塞或在途执行时拒绝。
只新增内部执行轮次，不重启 VREG、不增加公开节点；保存请求不等于实际执行。
旧验证、验收和结果能力不计入新轮次，历史报告/文件与批准记录保留；新结果独立验证和验收。
失败同 seed 重跑属于失败分析，与整组重新回归和计划 repeat 分开计数。
`RegressionBatchManifest/2` 与 `RegressionEvidence/3` 将执行记录绑定当前方案和轮次；
重复或漏跑、混入其他 group/profile、旧轮次记录均不能验收。Dashboard 保存后重新读取
当前权威状态；未收到保存结果不自动重试，历史报告通过项目/节点/轮次受控接口读取。
coverage hole 或未关闭 regression failure 必须登记责任工作流和下一步动作。Main Agent
分析后向上游登记重规划或重验证要求；只有实际上游版本或证据变化才沿依赖图自动传播
`REVALIDATION_REQUIRED`，分析结论本身不会自动修改、批准或关闭上游节点。

全部必需 VDOC 正文形成当前有效的 `art.doc` 和 `cap.doc` 后，Dashboard 要求负责人选择：
“并行形成方案”或“按依赖顺序形成方案”。选择绑定当前 VDOC revision 和 capability
摘要并写入 ProjectStore。并行只表示 Main Agent 同时形成六类方案，不表示同时实施；
每个交付仍按 `cap.*` 门禁解锁。按依赖顺序模式先形成 VENV，然后依次开放 VREG 执行器、
VSTIM、VCHK、VCASE 和 VCOV；VREG 的结果方案仍等待 VCOV 与其他当前能力。
CLI 使用 `workflow-launch status` 读取同一状态；负责人可把其中的 `vdoc_signature` 传给
`workflow-launch choose parallel|dependency_order --reviewer NAME --vdoc-signature DIGEST`。
Dashboard 和 CLI 写入后都重新读取同一 ProjectStore 决定，不维护第二份启动状态。

添加和删除只登记下一版方案要求；重新启动需要填写原因并再次确认，不删除代码、
日志、证据、审批或历史节点，也不重启 Dashboard 或 Agent。旧项目提交新代码方案
时保留历史，旧批准不继承；无法确定新归属的旧依赖保持阻塞，等待 Agent 重新规划。
同一份公开方案若内容、工作流目标和决策均未变化，再次登记保持当前 revision、节点
和已完成审批，不会因前置能力仅变为暂时不可用又恢复而批量要求原文重批。前置能力
不可用期间仍阻止交付推进；恢复到原能力版本后重新读取当前状态。若方案、输入文件
或依赖的实际版本发生变化，受影响审批和证据仍须重新核对；负责人确认的工作流重启
总是创建新 revision，旧审批不自动继承。

VENV、VSTIM、VCHK、VCASE 增加补洞工作包，或删除、修改其他工作包时，新工作流范围
保留内容未变化工作包的原方案和交付节点。原节点版本、批准与证据继续按当前实际输入
核对，负责人无需重复验收同一交付。变更的工作包才建立新节点版本；工作流目标、决策
变化或显式重启不保留旧节点。详情中的 `revision` 绑定该节点版本，
`workstream_revision` 表示当前工作流范围版本；原始记录保留用于审计。

VCOV 增加、删除或修改收敛范围时，同样保留未变化的覆盖率实现方案和实现交付节点、
原节点版本、批准、验证及能力版本。实际输入、依赖版本、覆盖模型或证据变化仍按原规则
重新检查；不能仅因收敛方案换版而要求重新批准已有实现。收敛节点、排除文件和运行证据
仍绑定当前收敛范围；工作流目标、决策变化或显式重启不保留旧节点。

VREG 调整回归结果 group 时，也保留未变化的回归基础设施方案、交付节点及原批准。
执行器版本不会随结果范围一起更新，因此不会使原有激励、检查和用例发生审批级联。
基础设施的实际输入、代码或证据变化仍会使相关结论失效；结果方案及执行轮次继续按
当前结果范围核对，不能沿用旧轮次报告。

相同代码、原始证据和逐项检查结论再次登记时，登记文件改名或追加描述性摘要只增加
审计回执，不撤销原验收。ProjectStore 中已检查的回执是事实源；未登记的原始报告编辑
不能替换检查结论。专用证据报告、日志、代码、检查结果、依赖实际版本和执行轮次仍
参与版本检查。历史错误重建的执行器只允许在严格核对原批准及全部当前证据后恢复，
不创建审批，不迁移回归结果或执行轮次，有未核实结束任务时禁止恢复。

The v1 control plane uses five cooperating subsystems: VPlan, VModel, VCheck,
VClosure, and VReason. See the [mode catalog](skill_modes.md) for commands and
the [architecture summary](architecture.md) for authority boundaries.

Deterministic commands persist their result before returning. The explicit
`agent-service` supervisor can continue current VDOC and code-workflow actions using the selected
runtime; it never grants approvals or treats a process exit as verification evidence.
方案批准后，在线服务可继续对应交付节点的实现、采集、分析和验证；验证通过后等待负责人验收。
依赖尚未验收时不会执行对应交付；后台服务未启动时仍由当前交互 Agent 执行，审批本身
不会启动一个新 Agent 进程。VCOV 和 VREG 的旧项目记录仍可读取；旧通用方案/交付角色按其
完整能力要求显示 VCOV 实现或收敛类型、VREG 基础设施或结果类型。历史记录保持不变，
新方案分别使用各自的四种明确节点类型。

## CLI 重启与自动接续

运行 `scripts/setup --runtime kimi|codex --workspace-root PATH` 默认进入交互 CLI，
不因项目已经 bootstrap 而切换到后台服务。启动时自动提交一次接续任务：新项目
收集缺失输入；已有项目读取当前 revision、closure、审批和问题回答，执行允许的
下一项工作，直至需要负责人决定、工作完成或遇到明确阻塞。不是仅显示工具清单后等待。
Codex 使用原生交互启动提示；Kimi 在新建 TUI 输入框就绪后提交一次可见任务，
仍保留交互界面，不使用会在首轮后退出的 `--prompt`。需要真实终端和已登录的 CLI；
若无法识别输入框，明确提示手动提交，不向登录提示或旧会话发送任务。
`--interactive` 保留为兼容参数；`--no-agent` 只安装配置，不启动 CLI 或服务。

setup 在进入交互 CLI 前先检查 Dashboard。已有项目优先复用运行记录中的原端口，
服务停止时独立后台启动，项目注册缺失时补登记；然后核对服务所属账号、当前项目、
状态数据库可读性，以及带授权的项目接口、页面和脚本文件。还会比较服务启动时捕获的
代码版本与当前安装文件，包括未提交修改和 Python 路径；版本一致时复用，旧服务缺少
版本信息或版本不同则在原端口受控更新。更新前核对服务账号、进程和全部注册项目的
数据库兼容性，保留所有项目注册及原 token，不重启验证工作流或改变审批记录。
检查只读取项目、数据库身份、状态计数及工作流版本头，不读取整份方案或重新计算完成
状态；数据库持续变化时有界重试，稳定后仍不一致则阻止进入 CLI。检查会清除当前项目
的显示缓存并通知已打开页面重新读取；服务代码更新后页面自动加载新版界面，
有未提交输入或尚未确认结果的保存操作时延后刷新，避免丢失输入或误判审批保存结果。
没有旧运行记录时才按现有规则选择端口。
旧端口被其他服务或账号占用、权限不正确、数据不可读或页面检查失败时，setup 明确
报错并停止在进入 CLI 之前，不抢占端口、不停止其他项目、不静默切换端口。项目尚未
初始化时跳过此检查，由 bootstrap 完成首次注册；初始化记录不完整时不能当成新项目。
`--no-agent` 保持仅安装配置，也不启动 Dashboard。退出 Agent CLI 不会停止独立的
Dashboard。远端检查不代表本机 SSH 隧道正常，已有端口转发需保持连接。

Agent 已经在工作时，可在框架目录的另一个终端运行以下命令恢复 Dashboard，无需
打断 Agent，也不重新执行 bootstrap（请替换项目路径）：

```bash
.deps/runtime/venv/bin/python scripts/verif_harness.py dashboard \
  --project-root /path/to/project --ensure-ready
```

需要后台自动接续时，退出交互 CLI 后显式运行 `agent-service start`。
服务从同一个 SQLite 数据库读取当前 VDOC 和代码工作流允许的动作，串行调用所选 CLI 的非交互模式。
审批意见提交、批准全部内容及工程问题回答都先保存；服务随后重新检查当前版本并
执行允许的动作。注销或重新注册 Dashboard 不删除这些记录，也不终止该服务。

```bash
verif-harness agent-service status
verif-harness agent-service stop
# 等 status 显示 STOPPED 后，可按需重新启动或转入交互 CLI：
verif-harness agent-service start --runtime kimi
./scripts/setup --runtime kimi --workspace-root /path/to/project
```

服务与通过 setup 启动的交互 CLI 共用项目执行锁。切换前必须退出另一方；直接从
其他终端手动启动、不经过 setup 的旧 CLI 不受此锁管理，应先退出。服务不会向
旧 TUI 注入按键，也不会复活旧会话；每一轮从当前版本、审批和回答重新建立上下文。
Kimi 使用非交互 `--prompt`，探测到旧版 `--print` 时一并使用；它按 CLI 的非交互权限执行。Codex 使用
`exec --sandbox workspace-write`。使用前应确认项目可信、CLI 已登录且权限符合预期。
新版 Kimi 的受管轮次显式加载同版本随包提供的 Main Agent profile；不会覆盖你自定义的
交互 profile，也不依赖旧 profile 中仍可能存在的后台 await 指令。

服务可接续 VDOC、已批准代码交付以及已登记回归轮次；核心控制面不直接执行 EDA 命令，
Main Agent 仍通过项目已有工具执行并登记证据。服务不批准、冻结或发布。
回归请求保存只表示已登记；Agent 启动只表示接单。Agent 中断后若工具是否结束尚不明确，
轮次标为“外部任务状态待核对”，禁止重复启动；核对后须提交同轮次的真实证据。
存在阻塞问题时持久化问题并结束本轮，不依赖内存中的 await；回答后重新取任务。
同一输入只尝试一次，失败、未推进或意外中断会保留日志，不无限重试。
确认文件与记录后，先 stop 并等待停止，再运行 `agent-service retry` 和 start。
revision 改变时停止旧任务。重启后仍有旧子进程存活时拒绝另起，防止并行修改。
主机重启后须显式 start 恢复后台服务，或 setup 进入交互 CLI；服务不是系统开机启动项。

“Agent 交互”依次显示待回答问题、Agent 工作状态和交互历史。无负责人待办并不
代表 Agent 在线；服务失联会明确显示，运行日志保留在项目的
`.verif-harness/agent-service/`，成功退出也不代替 Main Agent 验收后检查与 closure。
节点中的待回答问题显示简短摘要和独立的“查看并回答”入口；长问题可展开完整原文，
不会把整段文字作为按钮。问题背景与证据默认折叠，问题正文、背景和选项说明支持
Markdown 段落、列表、表格和代码块，路径与命令按文本展示。折叠和排版不修改问题、
选项或审批记录；查看完整问题后仍通过同一问题记录提交回答。
Main Agent 提问时，先用一句话说明需要你决定什么，将当前结论、依据和还缺什么分段写入
背景，命令单独放进代码块。彼此独立的决定分别提问，不把多个决定、指标和长命令
混进同一段问题标题。
面向负责人的说明使用具体对象和动作，例如“这份报告对应第几次测试”“合并各次测试
生成的数据”“新增测试的结果”“按当前设计不会发生的情况”。出错时说明报告缺少了
什么，或系统的哪条要求与已批准方案不一致，再说明需要谁处理；不要用内部术语概括
不同原因，也不要在通俗解释后再次附上内部术语。原始文件、正式字段和审计记录保留原样。
重新打开 Dashboard 只读取状态，不会启动或唤醒 Agent。工作流 `ACTIVE` 表示方案已批准、
相关工作尚待完成，不表示 CLI 正在执行。只有当前 revision 的受管任务和新鲜心跳，
或仍有效的 assignment lease，才能确认活动正在执行；只有 `RUNNING` 历史登记而无
执行依据时显示“执行状态待核实”。原始登记保留用于审计，CLI 活动列表与 Dashboard
使用同一有效状态投影。已结束的子 Agent 不代表 Main Agent 当前正在处理。

## 文档撰写方案审批

`await-human` 与“需要你处理”都读取当前版本的节点审批和 Closure 动作，适用于
VDOC、VENV、VSTIM、VCHK、VCASE、VCOV 和 VREG。可重复传入 `--node NODE_ID` 只等待
指定节点；不指定时等待当前可处理的方案审批、交付验收或审批意见提交。节点批准
只唤醒 Main Agent 重新读取 Closure，不表示整条工作流已完成。VDOC 正文批准后仍须
执行 Main Agent 检查；仅保存意见不唤醒，提交整批意见才返回 `APPLY_REVIEW_FEEDBACK`。
`status WORKSTREAM` 的 `waiting_for_human` 是当前负责人待办的确定性集合；CLI 面向
负责人的摘要必须逐项使用该集合；其中可由 `await-human` 等待的正式评审另列在
`awaitable_reviews`，后台等待任务描述只能使用这个子集。`WAIT_FOR_DEPENDENCY` 表示
节点仍被前置能力阻塞，不得显示为当前待审批或待验收；显式传给
`await-human --node` 也会被拒绝。
返回的节点审批 ID 可用于下一次 `--after-review`，旧版本、变化的正文/证据或其他
项目的记录不能解除等待。超时不取消待办，也不能唤醒已经退出的 Agent。
工作节点列表没有当前负责人动作时不提示重复批准；禁用的列表审批按钮显示为灰色。
待办与 Agent 摘要区分方案审批、验证交付验收和意见提交。旧 Activity 仍记录等待、
但当前不存在对应待办时，显示“等待状态不一致”，要求 Agent 重新核对节点；
不把历史等待记录当作新的负责人动作。这里的审批等待不包含 runtime 原生的命令授权。

在工作节点列表的对应行，或文档撰写方案详情中点击“批准全部内容”，确认审批人
后即可提交，批准说明选填。两个入口使用同一节点、版本和审批记录。
这表示批准当前节点的全部方案内容，不要求先提交新增、删除或修改意见。
当前没有审批意见时，“批准全部内容”直接可用。登记新增、删除或修改意见后，
该按钮立即禁用；负责人使用“提交当前 N 条审批意见给 Agent”一次提交本节点
当前尚未处理的全部意见。提交意见不产生批准结论。Main Agent 分析、修改并登记
处理结果后，负责人重新查看当前内容，“批准全部内容”才恢复可用。
提交动作会解除仍在运行的 `await-human` 检查点并返回 `APPLY_REVIEW_FEEDBACK`；
若交互 Agent 已退出，在线的自动接续服务会取走当前批次；服务未启动时，批次
持久化等待下次 setup，不会伪装成已经处理。

交互 Kimi 对正式节点决定使用后台 `await-human`，不得把“批准全部内容”或“验收通过”
登记为 `agent-question` 选项。收到决定后，Main Agent 先在当前对话回显节点、revision、
已记录决定和下一步，再重新读取 Closure 并继续；后台检查点超时时，只要同一待办仍存在就
续建检查点，不能另建工程问题或自行假定批准。`agent-question` 回答只代表工程输入，历史记录
会明确提示它不等于节点审批或交付验收。

输入依据默认折叠。RTL、验证环境、参考模型和验证脚本只列目录；规格和其他文档
保留完整文件列表。代码的逐文件版本记录仍保留在折叠的审计详情中。
审批成功并刷新状态后自动收起侧边详情；完整节点页面则返回工作节点列表，不关闭
浏览器标签页。已通过的节点显示禁用的“已批准全部内容”，不会重复提交。

提交时立即显示“正在提交”，同一表单不能重复提交。服务端保存审批并更新当前
工作流后，先返回保存结果，再单独读取项目状态；页面不再等待整个项目的数据
生成后才提示审批已保存。此操作不批准正文内容，也不改变其他工作流的审批。

VDOC 工作流进度同时统计必需的文档撰写方案节点和正文交付节点。正文交付节点
尚未登记时，每个必需撰写方案先保留一个待登记交付节点，因此方案全部批准后
只完成方案部分，不会把整个 VDOC 显示为 100%。登记多个独立正文验收节点后，
进度分母按实际必需交付节点更新；产物、可用状态和文档内部清单不另计进度。
其他工作流同样只按当前 revision 的必需公开节点计算比例。如果节点统计看似全部完成，
但仍有待 Agent 处理的新增、删除、重验证要求，或 closure 与节点统计互相矛盾，Dashboard
不会显示 100%，而是显示“待处理”及导致无法完成的当前动作。历史回归轮次、旧 revision
和累计 Activity 不进入当前进度。

负责人提交“添加节点”“删除节点”或修改要求后，请求只写入 ProjectStore，不直接改动当前
节点。closure 会生成 `APPLY_WORKFLOW_CHANGE` 交给 Main Agent 分析并形成下一版方案；这条
已提交请求属于 Agent 待办，不会再次出现在“需要你处理”。请求在 Agent 明确记录处理结论前
持续阻止工作流完成，旧节点、审批、正文和审计历史保持可追溯。

工作节点列表按“节点名称、节点类型、进度、状态 / 操作”对齐排列，父子节点名称
使用相同的起始位置，展开按钮单独占位。正文内容验收节点下方标出对应文档名称和
文件名，可按文档名称或文件名搜索。列表进度使用带百分比的圆环，旁边保留计算指标，
悬停圆环可查看计算依据；运行和等待状态有轻微呼吸效果，完成或失效后停止，系统
启用“减少动态效果”时不播放动画。动画不代表 Agent 正在运行，也不改变完成比例；
负责人批准正文但 Agent 尚未检查完成时，仍不计为正文验收通过。状态徽标显示当前
方案审批或正文验收状态，进度单独显示完成比例；仅存在待执行的 Agent 检查动作时
显示“等待 Agent 检查”，不能在没有运行中 Activity 的情况下显示为“正在检查”。

列表默认按验证推进顺序稳定排列：同一文档或 `implementation_key` 的方案与交付相邻，
明确依赖的前置节点在前，覆盖率实现先于覆盖率收敛，回归基础设施先于回归结果；同一
阶段中计划要求完成的节点先于补充工作，最后沿用当前 proposal 的登记顺序。审批、
Activity 或更新时间变化不会让节点自动跳位。页面可临时筛选“需要你处理”或“Agent 工作”；
前者读取当前快照中的负责人待办，后者只显示已登记为 Agent 执行、等待领取或等待主 Agent
协调的 Activity。筛选只改变当前标签页的显示，不修改 ProjectStore、节点状态或方案顺序。

如果审批已经保存但页面刷新失败，会明确显示“审批已保存”，可点击“刷新审批
状态”重新读取，不会重复提交审批。请求超过 30 秒或连接中断时，可能已经写入，
请先刷新并检查该节点的审批历史，不要反复点击确认。审批人仍为必填，过期方案、
无权限或存在待处理问题时仍拒绝审批。

## Dashboard 状态刷新

文档内容验收节点与撰写方案节点使用相同的详情和审批布局，仅把方案内容换成当前
Markdown 渲染后的正文。抽屉、完整节点页和旧正文验收链接均显示同一内容，不再提供
二次“进入正文验收”入口、通用状态卡或重复验收表单。审批区只有新增、删除、修改
意见、“提交当前 N 条审批意见给 Agent”、批准全部内容和历史记录；批准说明选填，
批准成功后返回节点列表，不关闭标签页。存在尚未提交或尚未处理的审批意见时禁止
批准正文；意见处理完成后才允许负责人重新查看并批准。
正文验收节点的列表行也提供“批准全部内容”，无需先进入详情。点击后先通过受控 API
读取正文并核对文档、节点和当前版本，再打开同一确认弹窗；正文不可读或版本变化时
拒绝打开审批，项目切换或离开当前页面后不使用迟到的读取结果。已批准时列表与详情
均显示禁用的“已批准全部内容”，但仍等待 Main Agent 检查后才能算验收通过。
正文批准后仍可提交意见，旧批准随之失效，Agent 必须检查最新意见。正文读取失败或版本
变化时禁用提交；未回答的问题仍在节点内处理。界面统一不改变正文验收的独立完成条件。

正文已同步、交付节点已登记且前置方案已批准后，控制面为每个待验收节点生成
“负责人验收正文”待办。CLI、Dashboard 工作流摘要和“需要你处理”使用同一结果；
点击待办直接进入对应节点。正文缺失、尚未同步或有待回答的问题时，不重复催促验收。
提交验收结论后，待办转为 Main Agent 检查；检查完成及节点问题解决前不算验收通过。
旧版本的验收或 Agent 检查不能遮住新版本正文的待办。

存在文档变更记录时，工作流仍保留原有生命周期和风险记录，但主标题优先说明当前
需要谁处理什么，例如“等待负责人验收 8 份文档正文”，不把首次验收说成重新评审。
这不会清除风险、代替负责人批准正文，也不会把方案批准计作正文完成。

Dashboard 读取当前项目时，会按控制状态事务版本和已登记文档的变化指纹复用同一份
权威快照。实时事件流每秒只检查轻量变化指纹；审批、Agent 问题、节点、证据等
控制状态由 SQLite 触发器在同一事务中递增版本，不依赖远程或共享文件系统延迟的
文件时间戳。项目状态或文档没有变化时，不重新生成、序列化或传输整份项目数据。
控制状态版本、项目清单或已登记正文发生变化后，缓存立即失效并重新读取
`ProjectStore`，所以缓存和事件流都不是第二套事实源。
Agent 服务 heartbeat 只更新时间戳且在线状态没有跨过失联边界时，不使快照失效；
Activity 进度、任务状态、审批、问题、证据或租约失效等可见状态变化仍会递增版本。
如果首次 snapshot 或后续事件流恰好与连续 CLI/Agent 写入竞争，页面保持连接并显示
“连接正常 · 状态同步重试中”，每秒重新读取；读取稳定后发送最新 snapshot，
无需负责人手动刷新或重复提交审批。连接恢复但状态版本未变化时也会明确结束重试状态。
非竞争类读取错误会停止重试并说明失败原因，不把数据库或项目错误伪装成持续同步。

未命中缓存时，一次页面刷新只读取一次各工作流的方案，批量读取节点状态和依赖，
并在本次刷新内复用正文验收检查结果。文档内部清单仍须由 Main Agent 检查，不因
取消隐藏工作节点而省略检查。文档预览只读取已登记正文及其版本信息，不再连带加载整个
工作流方案；仍检查项目归属、文件是否存在以及正文是否变化。下一次刷新重新读取
当前状态，不跨请求复用方案审批或正文验收结论。

### 大方案的读取与写入成本

| 路径 | 处理方式 |
| --- | --- |
| 方案审批、正文验收、Agent 验收后检查 | 同一次操作复用已读取的方案；状态、revision 和内容版本仍重新核对 |
| CLI 状态、完成条件计算、Agent 任务分配与心跳 | 共用方案读取入口；未变化的完成条件不重复写入，仍检查任务租约和前置条件 |
| 文档同步 | 未变化时不写数据库；多文档变化统一计算后续工作、每种导出文件最多写一次 |
| 变更传播、影响查询 | 一次读取关系图，批量更新受影响节点；文档版本、内部清单检查和所有阻塞仍参与判断 |
| 状态摘要、模型 Markdown 导出 | 只读取实际使用的字段，不加载无关的完整证据内容 |
| 核对审批结果 | 使用当前项目的 `/api/approval-status?project=…&node=…`，不生成整个项目页面 |

SQLite 新增由触发器在同一事务内维护的轻量方案索引。首次打开旧数据库时自动补建，
不删除原方案、审批或历史。方案正文变化会更新索引中的内容版本，包含同一 revision
内的修改；状态变化不会迫使同一次操作再次解析整份正文。复用数据仅存在于当前调用，
不同线程和项目不共享；异常或操作结束后丢弃。数据库连接离开使用范围后立即关闭。
读取期间项目数据变化时，Dashboard 重新读取；持续变化时由首次加载或现有事件流自动等待
稳定版本，不缓存混合版本。写操作已经保存但快照暂时仍在变化时，接口先返回保存回执，
页面再通过事件流核对最新权威状态，不把刷新失败显示成写入失败。

审批查询返回“已登记批准”不等于正文验收通过；Main Agent 检查和开放问题条件不变。
查询仍要求授权、项目和当前节点匹配；版本变化、目标失效或未收到保存确认时，不自动
重试审批。审批核对接口及其按钮由 HTTP 测试和 Chrome 点击测试覆盖。

可用 `python3 tests/benchmark_store.py --units 3000 --payload-mib 100` 检查合成大项目。
该脚本只创建并清理隔离测试目录，不读取现有项目；输出各路径耗时、SQL 次数和完整
方案读取次数。`--directory` 可以指定测试目录的父目录，以比较不同文件系统。

面向负责人的快照只包含当前 revision 的公开工作节点、为审计保留的历史公开节点
及其直接关系。文档产物内部清单、逐文件来源关系和完整 closure
定义继续保存在状态数据库和审计接口中，不重复发送到页面；Dashboard 仍保留审批
所需的当前摘要、判断理由、完成条件、阻塞项和 digest。

### v2：批准的文档版本与下游依赖

公开节点和审批布局保持不变。后台记录以下结果，不增加负责人待办：

```text
文档撰写方案 → 负责人批准 → art.doc_plan（批准的方案版本）
  → Agent 撰写正文 → 文档内容验收节点
  → 负责人批准 + Main Agent 检查 → art.doc（验收的正文版本）
  → Engine 核对当前版本和依赖 → cap.doc（该文档可供下游使用）
```

每份文档独立建立结果，不要求无关文档全部完成。正式正文撰写前，仍须先完成
本轮全部必需撰写方案审批。下游依赖 `cap.doc:<document_key>`，不能把方案批准、
模板存在或有条件接受当作正文可用。正文变化会使正文产物与下游可用状态失效；
没有变化的撰写方案可保留。方案范围或上游输入变化则按依赖关系重新检查。
旧产物版本保留当时的正文、方案、审批引用和检查清单，不覆盖历史记录。

Agent 使用 `docs manifest NODE` 读取当前清单，核对要求、来源和正文各节后，
再执行原有 `agent-review-check complete`。该操作同时保存当前版本清单的检查
记录，不自动替负责人批准。`docs artifacts` 可查看产物版本与当前可用状态；
`docs artifacts --artifact art.doc:verification-plan --version 1` 可读取某一历史版本。
状态及正文文件均未变化时，不重复构建产物，也不因查询而写入新版本。
重复登记相同的文档撰写方案或正文交付范围，保留原节点、版本和有效审批。
对同一审批、正文和完整清单重复执行 Agent 检查时，检查时间和描述性说明仍记录在
检查记录中，但不会生成新的正文产物或下游能力版本，也不会要求下游重复审批。
已批准的同一版本不能重复批准；新增修改意见、真实正文或输入变化以及显式重启仍须
按原规则处理。待处理的负责人变更要求不能用重复提交旧方案来消除。

v1 项目首次由 v2 打开时自动迁移：公开节点定义和负责人审批保持不变；旧隐藏
节点、证据、检查和活动保留为历史，开放问题移到所属公开节点；旧运行任务失效。
原 Main Agent 检查重新进入待检查状态，须按当前正文和清单复核，不能自动通过。
升级前应备份项目的 `.verif-harness`；迁移后的项目应继续使用 v2，不要用 v1
重新生成隐藏节点。本次仓库升级不会主动操作或重启远端已有项目。
