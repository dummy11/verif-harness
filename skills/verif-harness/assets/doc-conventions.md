# Document Conventions

All Stage 0 documents generated by the verif-harness skill must follow these
conventions. `.harness/check_ai_workflow.py` enforces the mechanical parts.

## Structure of every doc

1. **Top-level heading** — `# <Doc Title>` matching the file's purpose.
2. **Purpose paragraph** — one paragraph, plain prose, no bullet list.
3. **Body sections** — doc-specific content. See per-doc guidance below.
4. **待 Human Review 的假设** (if any) — bullet list of assumptions requiring
   human confirmation. Never use bare `## 假设` — the check script rejects it.
5. **开放问题** (if any) — bullet list of questions the human must answer.
6. **Review block** — copy from `assets/review-block.md`, tailored to this
   file's `### Project-Level References`.

## Per-doc guidance

### `<verif_root>/docs/roadmap.md`

- Purpose: list stages from Stage 0 (docs) → Stage 5 (coverage closure).
- Every stage must produce runnable code (except Stage 0). Never describe a
  stage as "empty skeleton" or "placeholder-only".
- Body sections: one `## Stage N — <name>` per stage, with Goals /
  Deliverables / Exit Criteria bullets.

### `<verif_root>/docs/harness_style_methodology.md`

- Purpose: record how this project applies harness-style methodology.
- Body sections: Background, Principles (doc-first, entry rules, prompt as
  bootstrap only, auto-checked docs, staged advance, ...), Current Status.
- Reference the reference-model spec ONLY if `reference_model.enabled` in
  config is true.

### `<verif_root>/docs/governance/verification_workflow.md`

- Purpose: define review gates and change-request rules.
- Body sections: Purpose, Core Principle, Governance Rules, Markdown
  Workflow, Required Reading, Stage 0 Review Model, Change Request Model,
  Implementation Rules, Review Output Format.

### `<verif_root>/docs/verification/verification_plan.md`

- Purpose: define overall verification scope, strategy, sign-off criteria.
- Body sections: DUT under test, Scope in/out, Verification strategy,
  Sign-off criteria (coverage %, test pass rate, assertion coverage).

### `<verif_root>/docs/verification/feature_matrix.md`

- Purpose: decompose DUT into verifiable features.
- Body: table with columns `Feature ID | Feature | RTL source | Notes`.
- RTL source column must cite the RTL file:line where the feature is
  implemented. If unknown, list under 开放问题.

### `<verif_root>/docs/verification/testcase_list.md`

- Purpose: enumerate tests with objective and priority.
- Body: table with columns
  `Test ID | Objective | Priority | Feature IDs | Notes`.

### `<verif_root>/docs/verification/tb_architecture.md`

- Purpose: define UVM/TB component layering.
- Body sections: Layer diagram, Component list (agent/driver/monitor/
  sequencer/scoreboard/reference model interface), Data flow.
- If reference_model.enabled is false, remove the reference-model row from
  the component list.

### `<verif_root>/docs/verification/assertion_plan.md`

- Purpose: define assertions on protocol / timing / safety properties.
- Body: table with columns
  `Assertion ID | Property | Location | Kind (immediate/concurrent) | Notes`.

### `<verif_root>/docs/verification/coverage_plan.md`

- Purpose: define functional coverage, cross coverage, closure method.
- Body sections: Covergroups, Coverpoints, Crosses, Coverage goals per
  stage, Closure strategy.
- Every entry must map to at least one feature in feature_matrix.md.

### `<verif_root>/docs/verification/reference_model_spec.md` (only if
`reference_model.enabled` is true)

- Purpose: mirror the upstream reference model semantics for this project.
- Body: **copy the technical content** from
  `reference_model.spec_path` (upstream) into this file, but replace the
  upstream doc's review block with a fresh Draft/Pending block from
  `assets/review-block.md`.
- The Revision Log's first entry must record the upstream source path so
  future divergence is traceable.

## Traceability rules

- Every claim about DUT behavior must cite `<rtl_root>/<file>:<line>`.
- Every claim about reference model semantics must cite the local
  `reference_model_spec.md` line, which in turn cites upstream.
- Never state a spec conclusion in imperative form without a citation or
  an entry in 待 Human Review 的假设.

## 决策生命周期约定

harness-style 工作流按确定性把"文档内的决策项"分为 **4 类**，文档整体的
**Lifecycle 状态**有 **3 类**。两者独立正交 —— 文档可以整体 Approved，
但内部仍有 Provisional 决策待后续 Stage revisit。

### 4 类决策 sections

每份 doc 尾部（在 review block 之前）**必备以下 4 个 sections**（即使某
section 内容为 `- None` 也保留占位）：

1. **Human Decisions**（在 `### Human Decisions` 内，属 File-Level Human
   Review 区块）—— 已冻结的架构基线。改动需 change request。命名：`HD-<n>`
   / `LD-<n>` / `H-<n>` 保持连续编号。
2. **`## 暂定决策 (Provisional)`** —— 项目已选定方向，标注依据 + 目标复审
   Stage + 影响面。允许 Stage gate 时重议。命名：`P<n>` 前缀。
3. **`## 待 Human Review 的假设`** —— Human 应决但尚未拍板，agent 按此推理。
   命名：无前缀，纯 assumption 描述。
4. **`## 开放问题`** —— 依赖**外部**输入（上游项目 / 第三方规格 / team
   之外）。命名：`OQ<n>` 前缀，含 `Depends on:` / `Blocks:` / `Status:`
   字段。

### 3 类 Lifecycle 状态

| Lifecycle | 语义 | Review Metadata Status | Change Request 需要? |
|----------|-----|----------------------|-------------------|
| **Draft** | 尚未 baseline review | Pending / Changes requested | 否 |
| **Approved** | 已 baseline review 通过 | Approved | Frozen Sections 里的项需 CR |
| **Living** | 已 baseline review，明确会随 Stage 演进增长 | Approved | 内容增改无需 CR，Frozen Sections 里的项需 CR |
| **Frozen** | 完全冻结基线 | Frozen | Frozen Sections 项需 CR |

Doc 类型建议（skill 生成的 10 或 11 份 Stage 0 文档，包含 `AGENTS.md`）：

| Doc 特性 | 推荐 lifecycle 目标 |
|--------|------------------|
| 架构基线（tb_architecture / verification_plan / verification_workflow / AGENTS） | **Approved** |
| 计划类（roadmap / methodology / assertion_plan） | **Approved** |
| 天然增长（coverage_plan / testcase_list / feature_matrix） | **Living** |
| 上游依赖（reference_model_spec） | **Living** |

### Provisional 决策格式

`## 暂定决策 (Provisional)` section 中每一条按以下格式：

```markdown
- **P<n>**: <决策内容简述>
  - **依据**: <为什么这么决 —— 参考 / 业界 / 经验判断>
  - **目标复审**: Stage N gate（或具体 milestone / 日期）
  - **影响**: <误决影响哪些下游 doc / 代码>
  - **Provisional since**: YYYY-MM-DD
```

示例：

```markdown
- **P1**: sign-off functional coverage 暂定 ≥ 98%
  - 依据: 业界 module-level 常用 95-98%，取上限保守
  - 目标复审: Stage 4 gate（regression 完成后由 project team 确认）
  - 影响: sign-off 判定；coverage_plan.md 覆盖率 Sign-off 段
  - Provisional since: 2026-07-06
```

### 开放问题 (OQ) 格式

`## 开放问题` section 中每一条按以下格式（真外部依赖，本项目内无法决）：

```markdown
- **OQ<n>**: <问题简述>
  - **Depends on**: <外部依赖对象——上游 project team / 第三方 spec / etc.>
  - **Blocks**: <阻塞本项目哪些 Stage 或功能>
  - **Status**: <当前状态 / 已建立的沟通机制 / owner assignment>
```

如果 doc 无 open questions（都已转 Provisional），保留 section 但写
`- None`。

### Stage Gate Re-review 惯例

每个 Stage 进入前（Stage N-1 exit → Stage N entry），systematic review 所有
Provisional：

- **保持 Provisional**：证据不足，更新"目标复审"到下一 Stage
- **升级为 Human Decision**：Stage 期间已获得决策依据 → 转到 Human
  Decisions section；若影响 Frozen Sections 走 change request
- **降级为开放问题 / 假设**：方向错误 → 转回 open question 并说明原因

产出 `stage_gate_re_review.md` 报告（skill 提供
`stage_gate_re_review_template.md` 模板）。

### 与生成 doc 关联

skill 生成 Stage 0 文档时（`SKILL.md §Step 3`）：

- 每份 doc 必备 `## 暂定决策 (Provisional)` 与 `## 开放问题` sections
  （空 → `- None`）
- 每份 doc 的 `## Lifecycle` 段 `Baseline` 字段填 `Pre-Stage 0`；review
  approved 后由 batch upgrade 脚本升级到 `Stage 0 approved` 或 `Stage 0
  living`
- Review packet（`stage_review_packet_template.md`）生成时打包所有 HD +
  Provisional + OQ，供 human review

## Assumption language

- Do write: "假设 s_acc_data 的 pack 顺序为 low-endian（open question, see
  §Open Questions）".
- Do NOT write: "s_acc_data 的 pack 顺序为 low-endian" as a standalone
  fact.
- The check script also blocks strings like `已确认结论` / `最终结论` /
  `已确认的验证基线` before Human approval — do not use them.
